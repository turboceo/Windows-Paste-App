三处边界，三种解法

判断一个桌面应用的工程质量，看的不是它有多少功能，而是它在"跨不过去的缝"上做了什么选择。 这个项目一共面对三条缝，而且三条都选了偏难但更正确的那一边。

1.1进程边界：一条通道，两个方向

前端和后端之间没有一堆细碎的 IPC 方法，只有一个 dispatch 命令，请求体是一个 serde 内部标签枚举。这个决定的好处会随时间放大：新增一个能力（分类标签、窗口最大化）不需要动 IPC 注册表，只需要给枚举加一个变体；前端的 bridge.ts 因此能压到两个导出函数， 组件层完全不知道 Tauri 的存在。

更关键的是反方向的对称：后端不返回结果，而是往同一条 host-push 事件流里推消息， 消息同样带 type 判别字段。这意味着"谁改的状态"被彻底交给了宿主——剪贴板线程新增一条、 托盘清空全部、前端点了置顶，走的是同一个 push_items / push_selection。 前端于是退化成一个纯投影：它不推导任何业务状态，只渲染最后一帧。

为什么这个选择适合剪贴板 因为剪贴板是外部事件驱动的。用户随时可能在别的窗口复制东西，这不是前端发起的请求， 而是一次推送。若采用传统的"请求-响应"RPC，前端就得轮询或额外开一条事件通道； 选用命令 + 推送的双向模型，等于一开始就把"谁都可能改变状态"这件事写进了协议。

代价也很直接：所有请求都排队在同一个 Mutex<AppState> 上，而 AppState 里既有数据库句柄又有全量条目列表。第 03 节会展开这一点。

1.2格式边界：一次复制是一组格式，不是一个值

这是整个项目最有含金量的部分，也是多数 Windows 剪贴板工具做错的地方。 Windows 剪贴板从来不是"存一段文本"，而是同一份内容以多种格式并列存在。 在资源管理器里复制一个文件，系统会同时提供 CF_HDROP（文件列表句柄）和 CF_UNICODETEXT（路径文本）；截图工具给的往往是 CF_DIB、 CF_DIBV5 和 CF_BITMAP 三份。

项目的读取侧按 Files > Image > Text 的优先级取"信息量最大"的那一份作为主类型 （clipboard.rs:148），这个顺序是对的：文件列表能降级成文本，反过来不行。 但真正漂亮的是写入侧——它不是把主类型还原成单一格式，而是把多个格式一起写回去：

一次回写，两个落点。你复制了三个文件，然后在聊天框里 Ctrl+V：得到路径； 在资源管理器里 Ctrl+V：得到文件。用户不需要知道格式这回事，而这份"不需要知道" 正是靠后端多写了十六行代码换来的。

剪贴板里同时躺着 CF_HDROP + CF_UNICODETEXT

资源管理器只读 CF_HDROP，于是贴出的是文件本身——三份 docx、pdf、png 原样落进目标文件夹，命名与时间戳都保留。

同一份剪贴板，未做任何额外处理

编辑器读不到 CF_HDROP，于是退到 CF_UNICODETEXT，贴出的是三行换行分隔的完整路径。发文件路径给同事、粘进 Git 提交信息，都直接可用。

图像条目：CF_DIB（40 字节 BITMAPINFOHEADER + BGRA 像素）

不是贴一段文本占位，而是真正的位图。截图可以直接进画图继续标注、进 Word 变成可裁剪的对象、进 Photoshop 变成图层。

上面三个页签说的是同一件事：剪贴板的正确抽象不是"一个值"，而是"一组格式"。 写入方把所有合理格式都放进去，读取方各自挑自己认识的，谁都不需要协商。 这个模型也正是 R5（CF_HTML）能低成本实现的原因——它只是再往这组格式里加一项。

图像的方向同样较真。读取时手工解析 BITMAPINFOHEADER，处理 24/32bpp、 每行四字节对齐的 stride、以及 biHeight 为正时的 bottom-up 行序； 还处理了一个很实际的坑——很多来源的 32bpp 位图 alpha 通道全是 0，直接透传会得到一张全透明的图， 所以做了 if a == 0 { 255 } 的兜底（clipboard.rs:346）。 回写时反向手工拼一个 40 字节头加 BGRA 像素，把 PNG 还原成真正的 CF_DIB （paste.rs:126），而不是偷懒贴一段文本占位。所以截图能贴回画图、Photoshop、Word。

设计判断 把"格式"当成领域概念，而不是实现细节。很多同类工具在数据库里只存一个字符串， 类型只是给 UI 换图标的标签；这里 Text / Image / Files 是三种真实的存储与回写路径， 数据库里 Type 字段决定的是读取分支、blob 归属和写回格式。这是抽象层次选对了。

1.3焦点边界：Ctrl+V 要落在"呼出之前"的那个窗口

这是最容易被忽略、也最容易做错的一环。天真的做法是：用户按 Enter 时调 GetForegroundWindow() 拿到前台窗口，再切回去。但那时前台窗口已经是面板自己了， 于是 Ctrl+V 会打进自己的 WebView——什么都没发生，或者更糟，触发了页面里的快捷键。

正确做法是把"记住目标"这一步提前到面板出现之前。项目在 toggle_panel 里就把前台窗口句柄存进 last_target_hwnd （lib.rs:176），此后整个会话都用这个快照：

顺序里每一步都不能换位置：隐藏必须在写剪贴板之前（否则隐藏动作本身会抢走刚设好的前台）， 等待必须在 SetForegroundWindow 之后（Windows 的前台锁机制会让切换异步完成， 立刻发键会打进旧窗口），而 SendInput 必须用扫描码级别的事件而不是 keybd_event，才能被游戏和部分终端正确接收。

一个还没被利用的钩子 PasteService::paste_item 成功之后没有做任何收尾，而 clipboard.rs 里其实已经准备好了一个 CLIP_PAUSED 原子开关和 set_paused() 方法—— 只是全项目没有一处调用它。目前靠"回写触发的 WM_CLIPBOARDUPDATE 会被 hash 去重挡掉" 来兜底，逻辑上成立，但属于用去重代替了本该显式的暂停语义。

1.4状态边界：置顶是一句"不会被淘汰"的承诺

容量修剪通常写成"超出 500 条就删最老的"，一句话，但会顺手把用户精心置顶的东西删掉。 这里把承诺写进了 SQL：只对 Pinned = 0 的行做 OFFSET，置顶项永久豁免。 更细的一点是，删行的时候把 BlobPath 一起取出来，文件同步从磁盘删掉—— 否则历史库会一直很干净，而 blobs/ 目录会悄悄涨到几百兆。

去重策略也值得记一笔：只跟最新一条比较 hash，而不是全表 SELECT。 这是一个 O(1) 的幂等检查——连续触发多次 WM_CLIPBOARDUPDATE（同一次复制常常会触发两三次） 只会入库一次。hash 还带了类型前缀，text:… / files:…， 避免不同格式的相同字节撞在一起。

代价、边界，和一份完整的缺陷清单

上面所有设计都不是免费的。这一节把账算清楚：有些是确凿的 bug，有些是资源泄漏， 有些只是没做完——按"会不会丢东西"排序，而不是按代码好不好看。 一共 9 组，前 3 组属于"不该带着上线"的级别。

3.1会丢数据的三处

这一组最该先修，因为它们损坏的不是体验，是用户已经存下来的东西。

3.2程序没有单例保护

这是个常驻进程：它注册全局热键、占用托盘、独占一个 SQLite 连接。而它没有任何单实例机制—— 没有互斥量、没有命名管道、没有 tauri-plugin-single-instance。 双击两次图标，就会开出两个完整实例。

连锁反应逐条都是可见的：第二个进程的 RegisterHotKey 失败（热键已归第一个）， 而它失败时静默退出这条线程（见 3.4），于是第一个实例的热键仍然可用——表面上"没事"， 但新弹出来的面板属于第二个进程。两个实例各自维护一份内存里的 AppState，你在 A 面板里删了一条，B 面板不会知道；两边都在监听剪贴板， 同一次复制会被写入两次（虽然 hash 去重会挡住，但推送和 UI 更新是双份的）；托盘上叠两个图标。 两个 SQLite 连接并发写，还没开 WAL，撞锁时 add() 的失败会被 let _ = 吞掉，条目静默丢失。

值得单独说一句的是：Mutex<AppState> 保护的是进程内的并发， 对跨进程毫无作用。开发者可能正是因为"我已经有一把锁了"而忽略了这件事—— 这是单例保护最容易被略过的地方。

3.3数据进得来，出不去

这是一个完全本地、跑了好几个月、存了五百条珍贵片段的应用，而它没有任何导入导出。 没有备份、没有迁移、换一台机器只能从头开始。更麻烦的是数据的形态决定了这件事不容易补： 历史分散在 SQLite 和一个按 sha256 命名的 blob 目录里，两者靠 BlobPath 一列关联， 拷贝 history.db 而不拷 blobs/，所有图片就会变成裂图。

三种导出格式的取舍
格式适合代价
JSON + 图片目录 最忠实：完整保留 Type / Hash / Pinned / Tag / CreatedAt 与原始 PNG， 可以做到无损往返，也是内部备份的默认格式。 不是人类可读的交换格式，图片仍然是散文件。建议打成单个 .zip， 里面 items.json + blobs/。
Markdown 给人看、给别的工具吃。按 Tag 分节，每条一段，图片用相对路径引用。 丢置顶与精确时间，但换到 Obsidian / Notion 里仍可用。 有损，只能单向导出，不适合当备份。
纯文本 / CSV 最省事，只有文本条目有意义。适合"我只想把复制过的代码片段捞出来"这个具体诉求。 图片与文件条目只能降级成一行说明。

导入侧比导出侧难，难点全在冲突与幂等：同一个 Hash 已经存在时是跳过、 覆盖还是新建一条？CreatedAt 用文件里的还是导入时刻的？Tag 撞名要不要合并？ 一个稳妥的默认是：以 Hash 为幂等键，已存在则只更新 Pinned / Tag 这类用户产出的元数据，不碰 CreatedAt。 这样同一个包导入十次，结果和导入一次完全一样——这正是 Hash 字段当初就存在、 却只被用于"跟最新一条比对"的价值没被榨干的地方。

一个顺带的收获 做导入导出会强迫你把"一条剪贴板记录"定义清楚——它到底包含哪些字段、哪些是内容、哪些是用户附加的元数据。 这个定义现在散落在 ClipboardItem 结构体、ClipItemDto 和 SQL 建表语句三处， 彼此并不完全一致（比如 DTO 多出 preview 和 imageUrl 两个纯展示字段）。 导出格式一旦定下来，它就成了这条记录的权威定义。

3.4单个 Mutex 装着整个世界

AppState 同时持有数据库句柄、全量条目、选中态、搜索词和列数，挂在唯一一把 Mutex 后面。剪贴板回调路径是：拿锁 → 写 SQLite → reload() 全表重查 → 把整表序列化成 DTO → emit。这些全部在锁内完成。

500 条上限把问题压住了，但它是有天花板的：图片条目在 DTO 转换时要读文件、做 base64 （state.rs:90），而每一次推送都会重编码全部可见图片。 用户连续按三下搜索键，可能触发三轮全表 + 全图重编码。列表里图片一多，面板就会开始顿。

现成的优化就在配置文件里 tauri.conf.json 已经开了 asset 协议，scope 精确指向 $LOCALAPPDATA/WindowsPaste/blobs/**，但代码里一次都没用过 convertFileSrc。也就是说这块基础设施是通的，只是没人走。 一条图片从几 MB 的 base64 变成一个几十字节的 URL，只需要改这一个函数。

3.5上下方向键与列数耦合（确凿的 bug）

前端把"下一行"硬编码成 delta: 4，后端用 delta.unsigned_abs() >= columns 来判断这是不是一次跨行移动。 列数等于 4 时一切正常；但当窗口被最大化、或者用户在大屏上拉到 5 列以上， 4 >= 5 为假，step 退化成 1——按 ↑↓ 会变成左右移动一格。

更深一层的问题是协议本身：用"位移量"编码"方向 + 语义"两种信息，让前端不得不猜后端的列数。 更干净的表达是让前端只说意图——{ type: 'move', axis: 'row', sign: -1 }—— 后端自己去乘列数。这是 1.1 里那个单一通道唯一没做彻底的地方。

3.6重复项策略会留下"幽灵副本"

去重只跟最新一条比。所以 A → B → A 的复制序列会得到两条 A。 常见的剪贴板应用在这里的做法是"触摸"而不是"插入"：命中重复时把那条的 CreatedAt 更新为现在，让它回到列表顶部——用户的心智是"我刚复制的东西应该在第一个"， 而不是"它被丢掉了"。

顺带一提，db.rs 的 trim() 每删一行都调一次 AppPaths::get() 重新拼路径、重建目录（db.rs:235）。功能无碍，但这是循环里的无谓 IO，挪到循环外即可。

3.7静默失败、死代码，和没被用上的索引

热键线程里，RegisterHotKey 返回 0（被别的程序占用）时，线程直接 return 结束，没有任何提示。用户装完软件按下 Ctrl+Shift+V 毫无反应， 而 Ctrl+Shift+V 恰好是 VS Code、Windows Terminal、Notion 都在用的组合——撞车概率不低。 这是本项目最需要补的一个反馈回路：注册失败应当弹一次提示并引导改键。

SetForegroundWindow 的返回值同样没检查，也没有 AttachThreadInput 之类的兜底。更现实的是提权窗口——UIPI 会拦住非提权进程的 SendInput， 往管理员权限的终端里粘贴会静默失败，用户完全不知道为什么没反应。

全项目零日志：let _ = 吞掉了几乎所有数据库写入和窗口操作的错误， lib.rs:206 那个 notify() 函数从来没被调用过。出了问题只能靠猜。

还有一处自相矛盾：项目在架构上坚持"宿主是唯一真相源"，可 ContextMenu.tsx:21 把 PRESET_TAGS 硬编码在前端。分类的领域数据跑到了视图层。

3.8输入法与可访问性

搜索框没有处理输入法的 compositionstart / compositionend 事件。 打"代码"这两个字时，拼音还没上屏就逐字母触发了查询——一次输入白跑四五次全表 LIKE '%x%' 扫描，中文用户每次搜索都要付这笔钱。

卡片是 <div> 加 onClick，不可聚焦、没有 role、 没有 aria-*，全局还设了 user-select: none。 键盘能用是因为另写了一套全局钩子，但屏幕阅读器读到的是一堆无语义容器。 这不影响"能干活"，但它是应用商店与无障碍审计里的硬伤。

3.9缺失的能力

没有暗色主题（令牌已经集中在 :root，加一套 prefers-color-scheme 的覆盖成本很低）；没有富文本——所有文本都被规范化成纯文本，从网页复制带样式的段落会丢格式， 这是与 Paste.app 差距最明显的一项；搜索没有防抖，且是 LIKE '%x%' 全表扫， 走不了索引；CSP 为 null，对纯本地应用风险可控，但仍是关掉的一道防线。

这份清单说明了什么 难点选对了、难点的实现也对了（第 01、02 节），但边界情况、错误路径、资源生命周期、 可访问性这一整类问题几乎全空。前者靠洞察力，后者靠工程纪律和测试覆盖—— 而这个项目一行前端测试都没有，npm test 只跑 cargo，且跑之前会先清空你的真实历史。
04 建议 R1–R17 P0 止血 → P3 结构

可以继续推进的设计

按"改动量 ÷ 收益"排。P0 是止血：不修就会丢数据或少东西。P1 是当天能做完、 立刻能感觉到的。P2 是体验分水岭。P3 是结构升级，值得单独立项。

P0先止血：不修就会丢东西
R1

自检不许碰真实数据库改动 ≈ 10 行

最优先。把 --selftest 与 --seed 的库路径改到 %TEMP%\WindowsPaste-selftest\{pid}\，跑完连同 blob 目录一起删掉。 更彻底的做法是给 AppPaths::get() 加一个 root_override: Option<PathBuf>， 让"用什么库"变成一个显式参数而不是环境里隐式的 LOCALAPPDATA。 在修好之前，应该先把 test:selftest 这个 npm script 从 package.json 摘掉， 避免有人手滑清空自己的历史。

R2

blob 文件的删除要跟上行的删除改动 ≈ 15 行

clear() 已经把待删文件列表返回了，调用方却丢掉不用；delete() 干脆不返回。把两者都改成返回 Vec<String>，由调用方统一删文件， 或者更省心——把删文件下沉到 Database 内部，让它自己持有 blobs 路径。 顺带补一个"启动时扫描孤儿 blob"的清理（列出目录里不在表中的文件，删掉）， 这样历史遗留的泄漏也能自愈。

R3

单实例：第二次启动只是唤回面板改动 ≈ 5 行

接入 tauri-plugin-single-instance，回调里直接调 toggle_panel(app)。 语义上正好——用户点第二次图标，本来就是想要那个面板，而不是想要第二个进程。 这一步同时消灭了两个托盘图标、双份剪贴板监听、以及两个 SQLite 连接并发写同一文件的隐患。 顺手把 SQLite 切到 WAL 模式（PRAGMA journal_mode=WAL）， 让"万一真有第二个人打开这个库"时不至于直接撞锁失败。

R4

DIB 解析加长度校验，content 入库截断改动 ≈ 15 行

前者是安全边界：from_raw_parts 之前先用 GlobalSize(hmem) 核对头部声明的 header_size + row_stride × height 不越界，越界就放弃这条。 后者是内存与 IPC 边界：content 入库时截到 8KB（preview() 仍然只取 200 字符）， 并在 UI 上标一句"内容已截断"。两处都是几行的事，但一个防崩溃、一个防卡顿。

P1低风险，当天可完成
R5

图片改走 asset 协议，别再塞 base64改动 ≈ 5 行

把 ClipItemDto::from_item 里的读文件 + base64 换成 convertFileSrc(blobPath)。图片负载从"每张几 MB、每次推送重发" 变成"每张一个 URL，WebView 自己按需加载并缓存"。IPC 体积、内存峰值、滚动卡顿会一起好转， 而且配置里 assetProtocol.scope 已经写好了，不需要动权限。

R6

修正上下键的列数假设改动 1 行

delta.abs() > 1 判语义、signum() 判方向、columns 只定步长。 顺手把前端那两处 delta: ±4 换成发送 axis: 'row'， 让"一行几张卡"这件事永远只由后端知道。

R7

重复内容"提到最前"，而不是丢掉或再插一条改动 ≈ 10 行

add() 命中最新 hash 时返回 false 之外，再提供一条分支： 命中任意历史项时 UPDATE CreatedAt 并把它移回列表首。这符合"我刚复制的应该在第一个" 的直觉，也顺带解决了 A→B→A 产生副本的问题。 这条同时是 R8 的基础——幂等的 Hash 查询正是导入功能的落点。

R8

导入 / 导出，用 Hash 做幂等键改动 ≈ 150 行

导出走「JSON + blobs 目录」打成一个 zip：items.json 里放 Type / Content / Hash / CreatedAt / Pinned / Tag，blobs/ 放原始 PNG。 这是唯一能无损往返的格式，也是备份的默认选项。另做 Markdown 导出（按 Tag 分节， 图片用相对路径）给人看，以及纯文本导出给"我只想把复制过的代码捞出来"这个具体诉求。

导入的关键是幂等：以 Hash 为键查库， 已存在则只更新 Pinned / Tag 这类用户产出的元数据， 不碰 CreatedAt；不存在才插入，并把 blob 写回 blobs/。 这样同一个包导入十次，结果与导入一次完全相同。 界面上给一个"将导入 N 条，其中 M 条已存在"的预览，别让用户盲点确认。

顺带的好处：IX_ClipboardItems_Hash 这个现在白建的索引终于有了用途， 导入时的存在性检查会真的走它。

R9

搜索防抖 120 ms + 输入法保护改动 ≈ 20 行

现在每次 onChange 都会触发一次全表查询 + 全量推送。加一个 useDeferredValue 或手写定时器，把连续输入合并成一次请求； 同时监听 compositionstart / compositionend， 拼音未上屏期间不发查询。后者对中文用户是必需项而不只是优化——现在打"代码"两个字 会白跑四五次全表扫描。

R10

暗色主题改动 ≈ 60 行 CSS

令牌已经全部集中在 :root，加一段 @media (prefers-color-scheme: dark) 覆盖同名变量即可， 组件一个都不用改。这也是对 1,017 行 CSS 那次投资的直接回报。

P2体验分水岭
R11

支持 CF_HTML，让"从网页复制"不丢样式需要改表结构

这是与 Paste.app 差距最大的一项。做法和文件那次"双格式回写"完全同构： 读取时若存在 text/html（CF_HTML），把 HTML 片段与纯文本一起存下来； 回写时同时写 CF_HTML 和 CF_UNICODETEXT。Word、飞书、Notion 会拿到带样式的版本，记事本拿到的仍是纯文本。项目已经证明过这个模式能跑通，复制一遍即可。

R12

粘贴变体：Enter 原样 / Ctrl+Enter 纯文本改动 ≈ 30 行

"粘贴为纯文本"是这类工具的招牌。实现上是在回写时只写 CF_UNICODETEXT 而跳过富格式——正好复用 R11 建立的双通道。再补一个 Shift+Enter（粘贴后回车）， 三个键位覆盖 90% 的粘贴场景。

R13

热键可配置，且注册失败必须说话改动 ≈ 40 行

热键写死在 hotkey.rs:62，冲突时静默退出。建议把组合键移到设置里持久化， 并在 registered == 0 时通过托盘气泡或首次启动的提示条告诉用户"这个组合被占用了， 点这里换一个"。静默失败是这个项目目前最伤的一处体验缺口——用户会以为是软件坏了。

R14

把 set_paused 接上：暂停监听 + 应用排除改动 ≈ 50 行

开关已经在 clipboard.rs 里躺着。托盘菜单加一项"暂停记录 30 分钟"， 再接一个"密码管理器窗口前台时不记录"的判断（取 GetForegroundWindow 的进程名做白名单）。剪贴板工具处理密码、验证码这类内容是刚需，也是它最容易失信的地方。

P3结构升级
R15

推送改增量，别每次发全表需要改协议

目前每次状态变化都推完整 items。改成 { type: 'patch', upsert: [...], remove: [ids], order: [...] }， 前端按 id 做 reconciliation。条目上千之后这是唯一能保持流畅的路径， 也为 R11 的富内容留出体积预算。

R16

拖拽粘贴，替代模拟击键工作量中等

面板里按住卡片拖到目标窗口，走 OLE DoDragDrop（或 tauri 的 drag 事件 + 原生 IDropTarget）。优势是不依赖前台焦点，也不会被"前台锁"或游戏的反作弊拦掉， 更绕开了 UIPI 对提权窗口的限制；SendInput 那条路径保留作为快捷键方式的兜底。

R17

全文检索，而不只是 LIKE工作量中等

LIKE '%x%' 无法命中索引。两种走法：SQLite FTS5（对中文需要自己分词， 可用 trigram tokenizer），或者对内容做规范化后维护一张倒排表。 如果只想要"够用"，也可以先给 Content 加一个前缀索引， 把"以某词开头"的查询变成快路径，模糊查询再回落到扫描。

如果只做四件事

前两件是止血，后两件是让它真正可用。加起来不到两小时。

  1. 让自检别碰真实数据库（R1）。现在跑一次 npm run test:selftest 就会把用户全部历史换成 50 条假数据。这个必须先修，或者先把那个 npm script 摘掉。
  2. 接上单实例（R3）。五行代码，消掉双托盘、双监听、双写库这一整串问题。
  3. blob 文件跟着行一起删（R2）。否则用户每删一张截图，磁盘上就多一个永不回收的 PNG。
  4. 热键注册失败时给个提示（R13 的最小版）。静默失败比功能缺失更伤—— 它让用户以为整个程序坏了。

再往后，真正的分水岭是 CF_HTML（R11）与导入导出（R8）。 前者补齐与 Paste.app 最大的一处体验差距，后者决定这个应用的数据到底属于用户还是属于这台机器—— 一个存了五百条珍贵片段、却没有备份出口的本地应用，本质上是在赌硬盘不出问题。
